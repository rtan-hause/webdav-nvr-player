# Store and Database Schema

`internal/store` is the only package that touches the database. It holds the **clip index** (cameras, clips, snapshots, and their processing state) and the **sign-in data** (users, sessions, settings). The same SQL runs on SQLite and Postgres. Only the schema files differ.

## Choosing the database

`store.Open(ctx, databaseURL, dataDir)`:

- **SQLite (default, `DATABASE_URL` empty).** Opens `DATA_DIR/nvr.db` with the pure-Go `modernc.org/sqlite` driver (no cgo, so the binary builds with `CGO_ENABLED=0`). Pragmas: `busy_timeout(10000)`, `journal_mode(WAL)`, `foreign_keys(1)`, `synchronous(NORMAL)`. The pool is capped at **one open connection**. That serializes writers and avoids `SQLITE_BUSY` entirely, and every query takes milliseconds, so readers don't notice.
- **Postgres (`postgres://` or `postgresql://`).** Uses the `pgx` stdlib driver with up to 10 open connections.

`Open` pings the database and applies migrations before returning. `Dialect()` reports `"sqlite"` or `"postgres"`, which the status page shows.

### Placeholders

Queries are written with `?` placeholders. For Postgres, `Store.q` rewrites them to `$1, $2, ...`. This only works because no query contains a literal `?`, which must stay true.

### Migrations

SQL files are embedded from `migrations/<dialect>/NNNN_name.sql` and applied in name order. The version number is the prefix before the first `_`. A `schema_migrations(version)` table records applied versions. Each file runs in one transaction, split on `;`. That means migration files must not contain semicolons inside statements (for example in string literals or function bodies). New migrations need a file for **both** dialects with the same number.

| Version | Content |
|---|---|
| `0001_init` | `cameras`, `clips`, `snapshots` and their indexes |
| `0002_auth` | `users`, `sessions` (token hash only), `settings` |

The Postgres schema differs only in `BIGINT ... GENERATED BY DEFAULT AS IDENTITY` keys and `path TEXT COLLATE "C"`. The `C` collation makes `path` comparisons byte-ordered, like SQLite's `BINARY`, which the prefix range scan in `LivePathsIn` relies on.

## Tables

### `cameras`
`(id, name, channel)` with `UNIQUE(name, channel)`. `EnsureCamera` inserts with `ON CONFLICT DO NOTHING` and then selects the id. Ingest caches the ids in memory.

### `clips`
Columns, grouped by role:

- **Identity:** `camera_id` and `path` (unique, relative to `WEBDAV_ROOT`).
- **What the file name says:** `start_ms` (UTC ms, parsed from the file name).
- **What probing learns:** `end_ms` (0 until probed), `codec`, `width`, `height`.
- **What the server says:** `size`, `etag`, `mod_ms`.
- **Work-queue state:** `status`, `error`, `attempts`, `next_attempt_ms`.
- **Thumbnail state:** `thumb_state`, `thumb_kind`, `thumb_path`, `snapshot_id`, `pair_deadline_ms`.

Indexes: `(camera_id, start_ms)`, `(start_ms)`, and `(status, thumb_state, next_attempt_ms)` for the work queue.

### `snapshots`
`(camera_id, path UNIQUE, ts_ms, size, etag, mod_ms, status, clip_id)`, indexed on `(camera_id, ts_ms)` and `status`.

### `users`, `sessions`, `settings`
See [Sign-in and Sessions](../auth/sign-in-and-sessions.md). `sessions.token_hash` is the SHA-256 of the cookie, indexed on `expires_ms` for pruning. `settings` is a key/value table written with an upsert.

## State machines (rows are the work queue)

There is no jobs table. The [Ingest Pipeline](../ingest/pipeline.md) dispatcher polls these columns.

**Clip `status`**

```
pending ──probe ok──▶ ready
   │  └─probe error──▶ pending (attempts+1, next_attempt_ms = backoff)
   └──too many errors / not MP4──▶ failed
any ──file gone──▶ deleted ──re-uploaded at same path──▶ pending (all derived columns reset)
```

**Clip `thumb_state`** (only meaningful while `ready`)

```
none ─PairClip─▶ snapshot  (closest unpaired snapshot in window found)
             ├─▶ waiting   (none yet; pair_deadline_ms set)
             └─▶ frame     (deadline already passed)
waiting ─snapshot arrives (PairSnapshot)─▶ snapshot
waiting ─deadline passes, last PairClip─▶ frame
snapshot/frame ─thumbnail made─▶ done     (thumb_kind = snapshot|frame)
              └─too many errors─▶ failed
done(frame) ─later snapshot pairs─▶ snapshot   (upgrade)
snapshot ─snapshot missing/unreadable─▶ frame (UnpairForFrame)
```

**Snapshot `status`:** `pending` (inserted) → `ready` (after `PairSnapshot`, paired or not) → `deleted`.

Both pairing directions (`PairClip` from a clip, `PairSnapshot` from a snapshot) join on the same `pairable` condition and order by the same `pairOrder`, so a clip and a snapshot are matched by one rule whichever arrives first: same camera, both `ready`, neither already paired, snapshot taken between `beforeMS` ahead of the clip's start and its end, closest to the start wins. How pairing decides is described in [Snapshot Pairing and Thumbnails](../ingest/snapshot-pairing-and-thumbnails.md).

## Key operations

| Method | Used by | Notes |
|---|---|---|
| `AddClips` / `AddSnapshots` | scans, webhook | Batch insert in one transaction. `ON CONFLICT(path)` only updates rows that are `deleted`, which revives them with every derived column reset. Re-adding a live path is a no-op, so scans are idempotent. Returns the number of rows changed. |
| `ClipsToProbe` | dispatcher | `pending` and `next_attempt_ms <= now`, newest first. |
| `SnapshotsToPair` | dispatcher | `pending`, newest first. |
| `ClipsNeedingThumb` | dispatcher | `ready`, due, and `thumb_state` in `snapshot`/`frame`, or `waiting` past its deadline. Newest first. |
| `NextWakeMS` | dispatcher | Earliest future pairing deadline or retry time, so the dispatcher can sleep exactly until work is due. |
| `SetClipProbed` / `SetClipFailed` | probe | `SetClipFailed` only changes rows still `pending`. A permanent failure sets `failed`. |
| `PairClip` / `PairSnapshot` / `UnpairForFrame` | pairing | Each runs in its own transaction. |
| `SetThumb` / `SetThumbFailed` | thumbnails | |
| `LivePathsIn(dir)` / `AllLivePaths` | deletion reconciliation | `LivePathsIn` range-scans `[prefix, prefix+U+10FFFF)` on the path index, then keeps only direct children. |
| `MarkDeleted(paths)` | reconciliation | Clips: status `deleted`, thumbnail cleared, snapshot unlinked, and the thumbnail file paths returned so the caller can delete them. Snapshots: only marked `deleted`. A thumbnail already made from a snapshot is kept. |
| `ClipsBetween` | `/api/clips` | `ready` clips overlapping `[from, to)`. So the start index can be used, it only scans clips that start within `MaxClipMS` (1 hour) before `from`. Clips longer than an hour would be missed at a window's left edge. |
| `LooseSnapshotsBetween` | `/api/clips` | `ready` snapshots with no clip. |
| `HasClipsBetween` | `/api/days` | Any `ready` clip starting in the range. |
| `Stats` | `/api/status` | Counts by status and thumbnail state, paired snapshots, cameras, earliest and latest clip. |

## Concurrency constraints

- The store is safe for concurrent use inside one process. Pairing decisions are serialized one level up by ingest's `pairMu`, so two workers cannot claim the same snapshot.
- Nothing coordinates *between* processes. Running two replicas against one Postgres would make both dispatch the same rows. Deploy exactly one replica (see [System Architecture](../architecture/overview.md)).

## Tests

`internal/store/store_test.go` runs every test against SQLite, and also against Postgres when `NVR_TEST_POSTGRES_URL` points at a database the tests may wipe. Covered: camera deduplication, idempotent add and revive, the probe queue and failures, pairing in both directions, thumbnail lifecycle and deletion, range queries and stats, and migrations being safe to re-run. `internal/store/auth_test.go` covers users, sessions and settings.
